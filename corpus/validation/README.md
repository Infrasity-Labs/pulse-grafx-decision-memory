# Human validation of the reference decisions and the questions

Status: **not done.** No human has reviewed any item. The reviewer is pending a named human with software engineering context; this folder holds only the blank sheets, the protocol and the tools. Until a v2 key exists, every score in this repository is scored against the model-authored key (v1) and is exploratory. The background is in [docs/HUMAN-VALIDATION.md](../../docs/HUMAN-VALIDATION.md).

## What is here

| File | What it is |
|---|---|
| `reference_review_sheet.json` | one entry per reference decision (22), plus the decisions the model review thinks are missing from the list. Human fields are `null`. |
| `question_review_sheet.json` | one entry per question (53) and per conflict task (2). Human fields are `null`. |
| `v2/` | does not exist yet. The reviewer creates it and writes `v2/reference_decisions.json` and `v2/questions.json` (formats below). Nobody else writes there. |
| `rescore/` | output of `scripts/rescore_with_key.py` once a v2 key exists. |

Every entry in the sheets carries a `model_note`. That is the observation of the model review (`corpus/reference_decisions_model_review.json`, `corpus/questions_model_review.json`, summary in `corpus/MODEL-REVIEW-REPORT.md`) copied in for convenience. It is labelled **model draft**. It is not a judgement of the human reviewer and no scorer reads it. The sheets are generated by `python scripts/make_review_sheets.py` (`--check` verifies they match the corpus); do not edit the generated `v1` and `model_note` parts by hand.

## Protocol

For every **reference decision** (22 entries of `corpus/reference_decisions.json`), confirm and record in `human`:

1. It is meaningful and correctly characterised as a decision, not a trivial code fact (`is_a_decision_not_a_code_fact`).
2. Its evidence points to the correct source file and the exact relevant lines (`evidence_file_correct`, `evidence_lines_correct`, with `corrected_files` and `corrected_lines` when not).
3. The citation and the claimed rationale are supported by the source, or are identified as an invented scenario rationale (`rationale_supported_by_source`).
4. Missing decisions visible in the code are considered for inclusion with an explicit scope rule (`scope_rule_for_missing_decisions` at the top of the sheet, and `include_in_reference_list` for each item of `missing_decisions_to_consider`). `decision` per entry: keep, correct or remove.

For every **question** (53), confirm and record in `human`:

1. Whether it is answerable from the permitted source material (`answerable_from_permitted_source`).
2. All valid decision identifiers, or equivalent supported factual answers, not just the one expected slug (`valid_decision_ids`, `equivalent_supported_facts`).
3. Which evidence is sufficient for a correct answer (`sufficient_evidence`).
4. Whether an abstention is required, and why (`abstention_required`, `abstention_reason`).
5. Whether the wording or the data generation makes the question artificially easy (`artificially_easy`, `artificially_easy_reason`).

For each of the two conflict tasks, record the valid decision ids in `valid_decision_ids`.

At the top of each sheet record: `reviewer` (a name or role of the human who did the review), `review_date`, `decisions` (a short account of what was decided and why), and `unresolved_disagreements` (anything the reviewer could not settle, including disagreements with the model notes). Leave `null` anything not reviewed and say so in `decisions`; a partly reviewed set is allowed only if the reduced scope is stated there.

## Versioning rule

- **v1 = the original keys.** `corpus/reference_decisions.json`, `corpus/questions.json`, `corpus/questions-model-authored.json` and `scripts/questions.py` stay as they are. They are never rewritten, so the numbers recorded so far stay reproducible.
- **v2 = the human-reviewed keys**, written only by the reviewer, to `corpus/validation/v2/*.json`. A v2 file names the reviewer and the review date. A v2 file written by anyone else, or by a model, is not a v2 key.
- The scoreboard keeps showing v1 scores. v2 scores are added next to them, from `scripts/rescore_with_key.py`, with the v1 numbers shown alongside. The change between the two is reported as it is, in either direction.
- Model arms are re-run only if question wording, accessible evidence or the tasks themselves change materially. A pure key change (more accepted slugs, corrected citation lines, a different list of unanswerable questions) is re-scored from the stored outputs without any model call.

## Formats of the v2 keys

`v2/questions.json`:

```json
{
  "version": 2,
  "reviewer": "<the human reviewer>",
  "review_date": "YYYY-MM-DD",
  "questions": [
    {"id": "d1", "kind": "answerable", "accepted_slugs": ["jwt-algorithm", "token-expiry"]},
    {"id": "d12", "kind": "unanswerable"}
  ],
  "conflict_tasks": [{"id": "t1", "accepted_slugs": ["no-refresh-tokens"]}]
}
```

`kind` and `accepted_slugs` are optional. A question that is not listed keeps its v1 key. `accepted_slugs` are the decision ids that count as right in addition to the v1 `expected_slug`. To drop the v1 slug, give `expected_slug` too. `answer_keywords` may also be given for questions answered without a named decision.

`v2/reference_decisions.json`: `{"version": 2, "reviewer": ..., "review_date": ..., "entries": [{"id", "files", "lines", "keywords"}, ...]}`, the same entry shape as `corpus/reference_decisions.json`. It replaces the reference list when the Recorder's recall is re-scored.

## Re-scoring

```
python scripts/rescore_with_key.py --questions-key corpus/validation/v2/questions.json --reference-key corpus/validation/v2/reference_decisions.json
```

This reads the stored outputs (`demo-state/arms/*.json`, the Recaller, retrieval and Recorder files under `demo-state/llm-runs/`, the first recorded Recorder run) and writes `corpus/validation/rescore/v1-vs-v2.json` and `.md`. It calls no model. What it cannot re-score is listed at the end of the markdown file and in the script's docstring: Reviewer outcomes, costs and tokens do not depend on the key; answers to a question whose wording the reviewer changed need a new run; the stored answers do not record which evidence an agent used.

## Acceptance (from the follow-up review, section 4.2)

A versioned, human-reviewed evaluation key; corrected citations; defensible multi-answer scoring; an account of how the revised judgements change the reported metrics; and a clear separation between independently validated findings and model-generated exploratory evidence. None of these is met yet except the multi-answer scoring code.
