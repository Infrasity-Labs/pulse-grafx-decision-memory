### auth-header-scheme
The Authorization header must hold a prefix and a token separated by one space, and the prefix must equal the configured jwt_token_prefix.
The API reads the Authorization header, splits it on a single space into a prefix and a token, and rejects it with 403 WRONG_TOKEN_PREFIX if the split fails or the prefix differs from settings.jwt_token_prefix. The default prefix is "Token" (app/app/core/settings/app.py:29). An optional variant returns an empty token when the header is missing.

### comment-ownership
Only the comment's author, matched by username, may delete a comment.
check_user_can_modify_comment returns true only when comment.author.username equals the current user's username. The delete route depends on check_comment_modification_permissions, which raises 403 when this check fails (app/app/api/dependencies/comments.py:43).

### favorites
Favoriting inserts a (user_id, article_id) row into a favorites join table and ignores duplicates.

The favorites table has a composite primary key on (user_id, article_id), and favorites_count and favorited are computed per read by counting rows.

### no-refresh-tokens
Sessions use one long-lived access token and the API has no refresh tokens.
The API issues a single access token that is valid for one week and has no refresh endpoint. A client that needs a new token logs in again.
Invented for this demo.
Reason: Security review SR-2025-14 of the pilot found that a stored refresh token let a stolen browser profile keep access for months. The team chose a one-week access token and no refresh token, so a stolen token expires on its own. Invented for this demo.

### hard-delete-articles
Deleted articles and comments are removed from the database, with no soft-delete flag.
Deleting an article or a comment runs a SQL DELETE. No deleted_at column exists.
Invented for this demo.
Reason: Legal review LR-77 requires that content its author deleted is gone from live storage within 24 hours. A deleted_at column was rejected because the rows would stay in the table. Invented for this demo.

### reset-link-lifetime
Password reset links stay valid for 30 minutes.
The API has no password reset flow yet. This fixes the rule for when it is built: a reset link works once and expires 30 minutes after it is sent.
Invented for this demo.
Reason: Support tickets showed that users open a reset mail within 10 minutes. A link that lives 30 minutes covers slow mail delivery without leaving a long-lived link in an inbox. Invented for this demo.

### reject-fancyhash
The fancyhash package is not used for password hashing because of its licence.
Password hashing stays on passlib with bcrypt. The fancyhash package was evaluated and rejected.
Invented for this demo.
Reason: The licence of fancyhash has a network-use clause that is not compatible with distributing the API. Passlib with bcrypt was kept. Invented for this demo.

### bcrypt-work-factor
bcrypt keeps the default passlib work factor.
No custom rounds value is set on the password context, so passlib's default applies.
Invented for this demo.
Reason: Load test LT-9 put the login endpoint at a p95 of 240 ms with the default factor. One step higher pushed it past the 300 ms login budget. Invented for this demo.

### postgres-over-mongodb
PostgreSQL is the data store and MongoDB was not chosen.
Articles, tags and favorites are stored in PostgreSQL tables joined by foreign keys.
Invented for this demo.

### aiosql-over-orm
Queries are hand-written SQL files, not generated by an ORM.
Every query lives in a SQL file that the repositories call by name.
Invented for this demo.
Reason: The DBA team reviews every query. A SQL file can be reviewed in a pull request and ORM output cannot (ADR-4). Invented for this demo.

### tokens-header-only

The API reads the token from the Authorization header. It does not set or read any cookie.
Invented for this demo.
Reason: Cookie transport would need CSRF protection that this API does not have (ADR-5). Invented for this demo.
