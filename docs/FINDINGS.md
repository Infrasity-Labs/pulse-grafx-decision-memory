# Findings and limits

What the runs found, and what they do not show. Evidence files are linked in each row. Differences from the plan and the docs, in full, are in [VERIFIED.md](VERIFIED.md).

## Limits

> [!IMPORTANT]
> - **Pre-release software.** Grafx is pre-alpha and Pulse is a 0.x line. This repo pins both and was verified on those versions only: okto-pulse 0.4.2 and okto-grafx 0.0.8, on 2026-10-29.
> - **One machine, one model.** Apple silicon, Python 3.12, `claude-opus-5-5`. The Linux runs are a container on a Docker Desktop VM on the same Mac, not a bare-metal Linux host. Run 1 is one run with answer-key prompts. The goal-based runs are five repeats per study, on fresh data homes ([SCOREBOARD](SCOREBOARD.md#live-runs-with-a-model)). The recall numbers show this setup. They are not a general accuracy claim. The timings are not a speed claim, and were not taken on an idle machine.
> - **The crash is a SIGKILL of the server process.** It does not cover power loss, disk faults or Windows. It ran in four recorded runs: three on macOS and one in a Linux container ([side by side](SCOREBOARD.md#crash-tests-side-by-side)). No acknowledged commit was lost in any of them.
> - **Reads happen with Pulse stopped.** Grafx read-only opens need a checkpoint-complete store, and a live Pulse owns its handles. The repo does not open a running Pulse's store from outside, and it never writes into a Pulse-owned store.
> - **Backup needs Linux.** Grafx 0.0.8 refused to take a backup on macOS, so that step ran in a Linux container, on a copy of the stopped store. Run in run 1's setup and again in the dated integration run.
> - **A killed server can block writes for about five minutes.** After a SIGKILL during commits, the board refused new commits until a writer lease expired in three of the four Kill B runs (305.8 to 310.6 s after the kill, on macOS and in the Linux container). In the fourth, a macOS run, writes were accepted 81.4 s after the kill with no refusal. Acknowledged commits were not lost.
> - **Search quality depends on the local embedding model.** It ran `sentence-transformers/all-MiniLM-L6-v2`, not the stub.
> - **Source-available, not open source.** Both products use the Elastic License 2.0 (Grafx adds a SaaS/Branding Addendum). This repo links to their licenses and copies none of their source.
> - **Questions and the reference list.** The dev and held-out questions were written by an assistant model, the model-authored questions by `claude-haiku-5-5`, and the 22-entry reference list by an assistant model after the first recorded run. A person has reviewed none of them.
> - **Invented data.** The scenario, the Maintainer's reason for the reversal, and the three shared conventions are invented. The only real code is the fork of `fastapi-realworld-example-app`.
> - **Graph runtime wording.** An older plan note said the Pulse README describes the graph runtime as LadybugDB. The README fetched on 2026-10-29 says Pulse uses Grafx only. This repo describes the installed 0.4.2 package and shows the commands that confirm it.

|---|---|---|
| Recall | ✅ Similarity and natural-language search put the right decision first every time. ⚠️ The decision-history tool returned no decisions for any sentence-length topic. Its semantic path returned nothing for the topics tried. Its non-semantic path returned the password decision for short keyword topics such as `bcrypt`. | [`history-probe.json`](../demo-state/step4/history-probe.json). Product observation, see [PRODUCT-OBSERVATIONS.md](PRODUCT-OBSERVATIONS.md#1-the-decision-history-tool-returns-nothing-for-sentence-length-topics). "0 of 10" on the scoreboard is this tool, not a defect of the demo. |
| Key Decisions | ⚠️ The "Key Decisions" list in the web UI is a Discovery intent served over REST. It is not an MCP tool in 0.4.2, so the Recaller could not call it. | [`history-probe.json`](../demo-state/step4/history-probe.json) |
| Contradictions | ⚠️ A `SUPERSEDE` override did not make Pulse flag a contradiction. `propose_reconciliation` still returned `ADD` with "no semantic match", although `get_similar_nodes` had just returned the old decision. The pair appeared only after an explicit `contradicts` edge in a second session. | [`step5/after.json`](../demo-state/step5/after.json) |
| Supersedence | ⚠️ The chain has length one from the new decision. From the old decision it returns length zero and still names the old decision as `current_active`. The `SUPERSEDE` commit reports `nodes_added: 0` although the new node exists. | [`step5/after.json`](../demo-state/step5/after.json) |
| Decision anchor | ⚠️ A cognitive `Decision` with a `spec:` source ref was refused with `kg_node_connectivity_violation`. The documented technical root is a ref that starts with `final_report:`. | [`walkthrough`](walkthrough.md#step-3-recorder) |
| Kill A | ✅ The uncommitted consolidation lives in server memory, so the kill discards it by design. Committing its old session id returns `session_not_found`. | [`killA.json`](../demo-state/step7/killA.json) |
| Kill B | ✅ No acknowledged commit was lost in four recorded runs. ⚠️ A server killed during commits left the board refusing writes with `lock_contention` ("another writer currently owns the board graph") until the writer lock's 300 second default TTL ran out. In the first Kill B attempt one in-flight commit survived without being acknowledged, and the restart log printed a `GuardedWriteError` traceback for a queued consolidation. | [`killB.json`](../demo-state/step7/killB.json), [extra sample](../demo-state/step7/extra-sample-killB-first-run.json), [log](../demo-state/notes/first-run-killB-restart-log.txt) |
| Leftover processes | ⚠️ After every SIGKILL, two `multiprocessing` helper processes of the killed server stayed alive with parent PID 1. They did not hold the board's files. They have to be stopped by hand. | [`ps` snapshot](../demo-state/notes/orphans-after-sigkill.txt) |
| Health after restart | ⚠️ Pulse reported `at_risk` with `health_probe_unavailable` right after the Kill A restart, and the board accepted a commit seconds later. A new board reports `at_risk` or `recovery_needed` for a while after creation (37 s in step 2, 68 s in step 6), and a commit sent before that returned `kg_health_state: recovery_needed_graph_readable`. | [step 2](../demo-state/step2/board.json), [step 6](../demo-state/step6/board2.json), [first attempt](../demo-state/notes/first-attempt-recorder.json) |
| Direct read | ✅ Read-only opens worked on both stopped stores, including the store of the killed server, and left every data file unchanged. ⚠️ `oktografx status --read-only` exits 6, "inconclusive", because no recovery ran on a read-only open. A read-only open still needs to open `bootstrap/first-open.complete` for writing, so it fails on a read-only mount (errno 30). | [`direct-read.json`](../demo-state/step8/direct-read.json) |
| Commit history | ✅ Enabled on both board stores. Pulse's adapter turns it on. The demo only reads that state and makes no history claims beyond it. | [`reader-*.json`](../demo-state/step8/) |
| Backup | ⚠️ Grafx 0.0.8 supports atomic directory publication on Windows and Linux only. On macOS it refused with `unsupported_operation`. The same procedure succeeded in a Linux container. | [`step9/`](../demo-state/step9/) |
| Store size | ⚠️ The `index` folder of a nearly empty decision board is 206744 KiB (408 files, about 507 KiB each), while `heap.dat` is 168 KiB. Cause, read from the installed okto-grafx 0.0.8 source and not reproduced by creating a store: an exact hash index gets one head page for every bucket when it is created (`engine/index_manager.py`, `_grow_buckets`, and `DEFAULT_BUCKET_COUNT` is 64 in `domain/index/keys.py`). With 8192-byte pages (`page_size` in `direct-read.json`) that is 1 header page plus 64 bucket pages, 520 KiB per index. 408 files at 520 KiB would be 212160 KiB, and the observed 206744 KiB is 97% of that. The size therefore comes from creating the indexes up front, not from the data. The source also has a sparse hash layout that creates bucket heads lazily; this repo did not check which layout each of the 408 files uses. The sizes in `store-layout.txt` are file sizes (`st_size`), not disk blocks used, so whether the files are sparse on disk was not checked either. | [`store-layout.txt`](../demo-state/step2/store-layout.txt), [`direct-read.json`](../demo-state/step8/direct-read.json) |
| Goal-based Recorder | ✅ Every one of 197 decisions in 11 runs cites a file, line and quote that exist. ⚠️ With no topic list it covered 7 to 10 of the 22 reference decisions (the answer-key run, told the topics, 12). It never wrote the decision about the shape of HTTP error bodies (0 of 11 runs), the one the Maintainer later reverses. | [`llm-runs/`](../demo-state/llm-runs/20261029T203549Z-4ffa2a8-dirty/), [SCOREBOARD](SCOREBOARD.md#live-runs-with-a-model) |
| Reviewer without the answer key | ⚠️ On a board that holds the decision, 5 of 5 Reviewers wrote the new decision with `supersedes` and `contradicts` edges, but only 1 of 5 flagged the old node as superseded. That one overrode Pulse's `ADD` hint with `SUPERSEDE` at commit. The other four left `superseded_by` empty, so the old decision still names itself as the current one when asked from its own id. On boards where the decision was missing (11 of 11) the Reviewer wrote nothing. | [`n-runs-reviewer-scripted-base/`](../demo-state/llm-runs/20261029T203549Z-4ffa2a8-dirty/n-runs-reviewer-scripted-base/) |
| Documented write format | ⚠️ Both goal-based prompts send the agent to the resource `okto-pulse://workflows/kg`. A headless Claude Code session cannot read an MCP resource unless it is given `ListMcpResourcesTool` and `ReadMcpResourceTool`. All 17 sessions without them said so and found the format by trial and error. This was a defect of this repo's harness, fixed in `run_agent.py --mcp-resources`. The Recorder's results did not change visibly. | [`run_agent.py`](../scripts/run_agent.py), study `resource-tool` |
| Graph against plain notes | ✅ The Recaller with the graph and an agent reading a text file of the same 32 decisions scored the same (one question apart) in five runs each, and both found the decision behind both conflict proposals. The code-only agent found none of the graph-only reasons, which exist only in the graph and the notes. The graph was not better than the notes. The agent session with the graph cost 3.05 times as much ($0.462 against $0.152, mean of 5): agent-session cost under the tested tool configurations, with different access per arm. It excludes building and maintaining the sources and is not a Grafx retrieval cost; the MCP tool catalog may contribute and was not isolated. | [`arms/`](../demo-state/arms/), [cost table](SCOREBOARD.md#agent-session-cost-under-the-tested-tool-configurations), [SCOREBOARD](SCOREBOARD.md#arms-side-by-side) |
| Unanswerable questions | ⚠️ The code-only agent answered "No, there is no rate limiting" and similar for four unanswerable questions, from the absence of a feature in the code. The scorer counts that as an invented answer. Whether it is one is arguable. | [`arms/llm-no-memory.json`](../demo-state/arms/llm-no-memory.json) |
| Linux | ✅ Kill A, Kill B, the direct read and 43 assertions ran in a Linux container with the pinned versions (CPU torch). Two harness defects showed up there and were fixed: `capture_versions.py` needed the `claude` binary, and the path scrubber turned `/repositories` into `<repo>sitories` when the repo sat at `/repo`. | [`linux-crash-*/`](../demo-state/linux-crash-20261029T205018Z-4ffa2a8-dirty/) |
| Prompts | The first attempt of steps 3 to 5 used prompts that left out `candidate_id` on edge candidates, which Pulse requires. Both prompts were fixed and steps 1 to 5 were re-run from a fresh data home. The saved prompts are the ones that produced the recorded outputs. | [`docs/prompts/`](prompts/) |
